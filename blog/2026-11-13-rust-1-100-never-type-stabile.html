Rust 1.100: il never type è finalmente stabile, cosa cambia per il tuo codice

Il 12 novembre è uscito Rust 1.100, e la notizia attesa da anni è una sola: dopo dieci anni e cinque tentativi falliti, il never type ! è stabile. Sembra un simbolo da nulla, ma tocca il sistema dei tipi nel profondo e porta con sé un piccolo cambiamento che rompe la compatibilità. Vediamo cos'è, come si usa con esempi concreti e cosa controllare quando aggiorni il tuo progetto.

Cos'è il never type, detto semplice

Il never type si scrive ! ed è il tipo delle espressioni che non producono mai un valore: un return, un break, un panic!, una chiamata a std::process::exit. Dopo di loro il codice è irraggiungibile, quindi il compilatore sa che "lì non arriverà nessun valore". Chi viene da Kotlin lo conosce come Nothing; in Java non esiste un equivalente vero, ed è per questo che a volte si scrive un return null finto dopo un metodo che lancia sempre un'eccezione, solo per far contento il compilatore.

La proprietà che lo rende utile è la coercizione verso qualsiasi tipo: siccome un valore di tipo ! non può esistere, Rust permette di trattarlo come un u32, una String o quello che serve. È il motivo per cui questo codice compila da sempre: 

fn parse_port(input: Option<&str>) -> u16 {
    let raw = match input {
        Some(s) => s,
        // `return` has type `!`, coerced to `&str`
        None => return 8080,
    };
    raw.parse().unwrap_or(8080)
}

Fin qui niente di nuovo. La novità di Rust 1.100 è che ora ! si può scrivere ovunque come tipo, non solo come tipo di ritorno di una funzione (-> !).

Cosa puoi fare adesso che prima non potevi

L'esempio più pratico è un Result che non può fallire. Con Result<T, !> dichiari nel tipo che l'errore è impossibile, e il compilatore ti lascia estrarre il valore senza unwrap() e senza un ramo Err fittizio: 

fn load_defaults() -> Result<Config, !> {
    Ok(Config::default())
}

fn main() {
    // irrefutable pattern: the Err variant cannot exist
    let Ok(config) = load_defaults();
    println!("{config:?}");
}

Utile soprattutto quando implementi un trait generico che prevede un tipo di errore associato, ma la tua implementazione non può sbagliare: prima si usava std::convert::Infallible, un enum vuoto creato apposta. Con questa versione Infallible diventa un alias di !, quindi il vecchio codice continua a funzionare e quello nuovo può usare direttamente il punto esclamativo.

Attenzione: un piccolo cambiamento rompe la compatibilità

Il never type ha richiesto dieci anni proprio per colpa della compatibilità. Per rendere Infallible un alias, il team ha dovuto cambiare il cosiddetto never type fallback da () a ! anche nelle edizioni 2015, 2018 e 2021 (nella 2024 era già così). Nella pratica non te ne accorgi quasi mai, ma può emergere in casi rari, per esempio quando ignori il risultato di una funzione che restituisce un tipo generico. In più il compilatore potrebbe segnalare come irraggiungibile codice che prima non segnalava.

Cosa fare in concreto, se hai un progetto Rust:

  • Aggiorna con rustup update stable e lancia cargo build e cargo test prima di toccare altro.
  • Se fallisce una dipendenza, prima di indagare prova cargo update: il team ha avvisato con largo anticipo e molti crate pubblici hanno già rilasciato la correzione.
  • Leggi i nuovi warning di codice irraggiungibile: spesso indicano un ramo che non aveva mai senso di esistere.
  • In CI fissa la versione con un file rust-toolchain.toml, così l'aggiornamento lo decidi tu e non arriva a sorpresa una mattina.

Le altre novità: allocatori e DropGuard

La seconda notizia grossa è la stabilizzazione della parte centrale dell'Allocator API: il trait Allocator permette di definire allocatori personalizzati e usarli con Vec e Box. Se stai imparando Rust puoi ignorarlo tranquillamente; se invece lavori su sistemi embedded, motori di gioco o codice dove ogni allocazione conta (arene, pool di memoria), è il pezzo che aspettavi. Per ora riguarda solo quei due tipi: il resto delle collezioni arriverà più avanti.

C'è poi DropGuard, pensato per eseguire una closure su ogni percorso di uscita da un blocco, che tu esca con return, con ? o normalmente: lo stesso bisogno che in Java risolvi con try/finally, qui espresso con il meccanismo di Drop già tipico del linguaggio.

Perché vale la pena capirlo anche se sei agli inizi

Il never type sembra un dettaglio da teorici dei tipi, ma insegna un'idea che serve in qualsiasi linguaggio: far dire al tipo quello che sai del programma. Un Result<T, !> racconta a chi legge, e al compilatore, che quell'errore non può capitare; un commento "tanto non fallisce mai" no. Più informazione metti nei tipi, meno controlli devi ricordarti di fare a mano. E il fatto che ci siano voluti dieci anni per farlo senza rompere l'ecosistema è una buona lezione su quanto conti la retrocompatibilità in un linguaggio usato da milioni di persone.
